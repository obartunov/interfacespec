# Какая часть BT-INV выражается без знания btree

Вопрос: какая часть каталога BT-INV.md записывается общим языком интерфейса
(InterfaceSpec), а какая требует знания btree.  Вывод сделан по 67 строкам
каталога и сверке законов opclass со вторым и третьим AM (hash, GiST/GIN)
по их документации.  Код для hash/GiST не писался.

## Классы

- **G** — формулируется через то, что есть у любого Index AM:
  поля `IndexAmRoutine`, протокол callback'ов, эталон результата.
- **P** — общий *вид* закона, но конкретный экземпляр зависит от
  AM: какая support-функция или стратегия какую роль играет.
- **B** — внутреннее устройство btree (страницы, L&Y, pin/LSN, safexid).
- **G/B** — обязательство общее, механизм его выполнения btree-специфичен.

Классификация — суждение по тексту контрактов, а не измерение.  Спорные
строки: A4 (формулировка ссылается на btree-стратегии; после
`amtranslatestrategy` её можно записать через CompareType), O13 (не
проверено, что AM, кроме btree, не передают NULL в support-функции), T14/T15
(свойство общее — «каждая индексируемая строка находится поиском»,
реализация в amcheck — btree).

**B целиком состоит из структуры и механизма конкурентности** — это
refinement-слой AMSpec.  В общий стандарт это не входит; от интерфейса туда
нужна только точка подключения (верификатор, injection points).

## Словарь, которого хватает для G

Он выведен из строк каталога, а не придуман заранее.

1. **Предикаты над `IndexAmRoutine`**: наличие callback'ов и импликации
   флагов (A1–A7, A9–A11; A8 снят при сверке).
2. **Эталон результата с профилем**: множество строк из seqscan с тем же
   квалификатором; профиль — exact / recheck (`xs_recheck`), ordered /
   unordered; **интервал допустимой неопределённости** при конкуренции (S6).
   Покрывает S1–S3, S6, S9, S13, U1, U3, U5, T14, T15, A6, A10.
3. **Автомат протокола скана** с постусловиями на `IndexScanDesc` после
   каждого вызова: S4, S5, S7, S8, S10, S11, V1, V7; истории с
   конкурентными транзакциями: U2, U4.
4. **Разделение ответственности без наблюдения**: V2, S12 — формулируются
   общо, но нарушение не видно на границе callback'ов.
5. **Время и сбой**: те же контракты после смены окружения (O12) и после
   replay (T16, V8).

Пункт 2 — центр стандарта: S6 превращает эталон из точного множества в
интервал [обязательно, допустимо].  Без этого сравнение с эталоном при
конкуренции даёт ложные расхождения.

## P: виды законов opclass

Все законы O и документированные законы других AM ложатся на семь видов.
Каждая ссылка ниже — текст документации или кода.

| Вид | btree | hash | GiST / GIN |
|---|---|---|---|
| K1 законы отношения (рефлексивность, антисимметрия, транзитивность) | O1–O3 | равенство — эквивалентность | — |
| K2 согласие двух реализаций одной функции | O4 (операторы и cmp), O5 (sortsupport) | стандартный hash и extended при seed 0 (hash.h:351) | — |
| K3 одностороннее приближение: в одном объявленном направлении ответ достоверен, в другом — «не знаю» | O6: ненулевой знак достоверен, 0 = не знаю | — | consistent: `false` достоверен, `true`+recheck = может быть (gist.sgml:300–316, gin.sgml:312); distance: оценка снизу (gist.sgml:870–876) |
| K4 конгруэнтность: равные ⇒ неразличимы для функции | O7 (образ) | равные ⇒ равный hash (xindex.sgml:1185) | — |
| K5 монотонность относительно заданного порядка | O8 | — | внутренний узел: distance ≤ distance детей (gist.sgml:874) |
| K6 перечисление по порядку (successor) | O9 | — | — |
| K7 замыкание K1–K4 по типам семейства и кастам | O10, O11 | xindex.sgml:1185, 1191 | — |

Наблюдение: O6 (abbreviated key) и GiST consistent/distance — один вид
закона K3, но с разным направлением достоверности.  Без параметра
направления K3 — ярлык, а не закон: по нему нельзя сгенерировать проверку.

Экземпляр закона определяется парой (вид, **таблица связей**): какой
номер support-функции играет роль компаратора, hash'а, equalimage; какая
стратегия соответствует какому отношению.  `IndexAmRoutine` знает только
количества (`amstrategies`, `amsupport`).

Уровень таблицы связей — **opfamily, а не AM**.  У GiST, GIN, SP-GiST и BRIN
`amstrategies = 0` (gist.c:63, ginutil.c:43, spgutils.c:48, brin.c:258):
смысл стратегий задаёт opclass.  Ядро уже решает это для стратегий на уровне
семейства: `gisttranslatecmptype` берёт support-функцию семейства
`GIST_TRANSLATE_CMPTYPE_PROC` (gist.h:43; gistutil.c, `get_opfamily_proc`).
`amtranslatestrategy` на уровне AM работает только там, где номера стратегий
фиксированы (btree, hash).  Для ролей support-функций аналога нет ни на
каком уровне.

Гипотеза (не проверена): таблицы «роль → стратегия / support-функция» на
уровне opfamily, по образцу `GIST_TRANSLATE_CMPTYPE_PROC`, вместе с
направлением для K3 достаточно, чтобы O1–O11 выводились без знания
устройства AM.  Для btree и hash таблица совпадает для всех семейств и
может задаваться на уровне AM.

## Насколько прототип привязан к btree

`opclass_laws.c` привязан к btree только через таблицу связей:
`BTREE_AM_OID`, `BTORDER_PROC` (роль компаратора), стратегии 1–5 (роль
отношений), `BTSORTSUPPORT_PROC`, `BTEQUALIMAGE_PROC`, `BTINRANGE_PROC`;
skip support — косвенно, через `PrepareSkipSupportFromOpclass()`.  Функции проверки — экземпляры K1 (O1–O3), K2 (O4, O5),
K3 (O6), K4 (O7), K5 (O8), K6 (O9).  Абстракцию «вид + связи» в коде не
вводил: пользователь пока один.

Существующая ручная проверка того же вида: `src/test/regress/sql/hash_func.sql`
для каждого типа отдельно проверяет K2 для hash (стандартный hash и extended
при seed 0).  Общий K2 на выборке значений заменил бы её для всех типов сразу.

## Что не выражается общим языком и почему это нормально

17 строк B: порядок на странице, high key, downlink, ссылки соседей,
posting list, suffix truncation, half-dead/deleted, pin/LSN-гейт, safexid.
Это не контракт интерфейса, а доказательство того, что реализация
выполняет G-контракты (S1, S6, V1, V3).  Общий стандарт требует от AM
выполнения G-контракта; B — способ, которым btree его выполняет.
