# D1-GIN: triConsistent через K3

Вопрос: выражается ли закон GIN `triConsistent` уже существующим K3, если
добавить только таблицу ролей и протокол вызова.

Opclass: `tsvector_ops` (стратегии `@@`, `@@@`).  Разбор источников —
GIN-SOURCE.md.

## Result

Да, с одним уточнением области значений эталона.  Закон K3 («доверенный
ответ совпадает с эталоном») не изменился.  Понадобились:

- таблица ролей GIN (4 строки, на уровне AM: номера support-функций GIN
  фиксированы, а смысл стратегий закону не нужен);
- роль `query_context(q) → {nkeys, keys, extra_data, null_categories}`:
  закон использует `nkeys`, остальное — непрозрачный контекст;
- протокол `key_vector` (адаптер: `extractQuery` → контекст, `check[]`,
  передача `keys`/`extra_data`/`null_categories` как есть, без
  интерпретации);
- источник значений: все векторы F/T/M длины `nkeys` и их доопределения;
- эталон, который сам может ответить «не знаю»: булевый `consistent` с
  recheck.  Такой эталон доверенный ответ не подтверждает.

| AM / opclass | закон | выражен | роли | значения | итог |
|---|---|---|---|---|---|
| GIN tsvector_ops | N1 (K3) | да | extractQuery, consistent, triConsistent, стратегии 1, 2 | 10 запросов, 424 пары «вектор → доопределение» на стратегию | pass: 408 доверенных из 848 |

848 = 2 стратегии × Σ 4^nkeys (на запрос с n ключами — 4ⁿ пар: F/T дают
одно доопределение, M — два).  Запросов с более чем 4 ключами в выборке
нет (такие пропускаются с пометкой).

## Как закон лёг на K3

    approx(p, q)    = triConsistent(p)               p ∈ {F,T,M}^nkeys
                      F → (0, false), T → (1, false), M → (1, true)
    trusted         = false_or_exact                 то же правило, что у GiST
    reference(c, q) = consistent(c)                   c — доопределение p
                      false → 0, true → 1, true + recheck → «не знаю»
    trusted ⇒ answer IS NOT DISTINCT FROM reference(c), для каждого c

`GIN_MAYBE` ничем не ограничен: документация требует только надёжности
определённых ответов, не точности (GIN-SOURCE.md).

## Контрольные примеры

Обёртка `d1ctl_tri` над `gin_tsquery_triconsistent` в контрольном
`ctl_tsvector_ops`:

| отказ | итог | контрпример |
|---|---|---|
| none | pass, 408 из 848 | — |
| tri_overconfident (MAYBE → TRUE) | FAIL | `strategy 1: check=M completion=F q='a' answer=1 flag=f reference=0` |
| tri_exact_claim (MAYBE → TRUE, только если во входе нет M) | FAIL | `strategy 1: check=TT completion=TT q='a' <-> 'b' answer=1 flag=f reference=unknown` |
| tri_first_completion (вместо MAYBE — ответ на первом доопределении, все M → F) | FAIL | `strategy 1: check=M completion=T q='a' answer=0 flag=f reference=1` |

Второй отказ ловится только через эталон «не знаю»: у фразового запроса
`consistent` на полном векторе отвечает true с recheck.

Третий отказ: ответ подтверждается первым доопределением входа и не
подтверждается вторым.  Его видит только проверка всех доопределений.

Красные пробы движка: «не знаю» подтверждает доверенный ответ;
состояния без M; одно доопределение вместо всех; recheck эталона
игнорируется — каждое даёт красный стенд.  Проба «только первое
доопределение» (`d1_completions(p) = replace(p, 'M', 'F')`) меняет итог
закона, а не только счётчик:

| отказ | все доопределения | только первое |
|---|---|---|
| none | pass, 408 из 848 | pass, 216 из 336 |
| tri_first_completion | FAIL | **pass**, 332 из 336 (неверный итог) |
| tri_overconfident | FAIL | FAIL |
| tri_exact_claim | FAIL | FAIL |

## Что изменилось в общем движке, и почему GiST и abbrev этого не требовали

| изменение | вид | почему раньше не было нужно |
|---|---|---|
| `source = ternary_completions`, `arity` | источник значений (G) | у abbrev и GiST вход приближения — сами значения выборки; у GIN — вектор присутствия ключей, которого в выборке нет |
| `strategies` | связывание ролей | у GiST эталон — оператор стратегии, номер стратегии приходит вместе с ним; у GIN эталон — функция без стратегии |
| эталон формы approx: «не знаю» не подтверждает доверенный ответ (`IS DISTINCT FROM` вместо `<>`) | область значений эталона | эталоны abbrev (comparator) и GiST (оператор) точны по построению; для них оба сравнения совпадают |
| выборка типизирована по элементу массива, а не по `opcintype` | источник значений | раньше выборка совпадала с типом входа opclass; у GIN это запросы (`tsquery`), а не `tsvector` |

Все четыре изменения — не в законе: K3 по-прежнему «доверенный ответ
совпадает с эталоном».  Расширение области эталона минимально: он может
быть «не знаю», и такой эталон ничего не подтверждает.

В движке по-прежнему нет имён AM и номеров (grep пуст); GIN-соглашение
о вызове — только в адаптере `key_vector`.

## Границы

| граница | нужная информация | почему метаданных недостаточно |
|---|---|---|
| вызов `extractQuery`/`consistent`/`triConsistent` | протокол `key_vector` | все три имеют `internal`-сигнатуры; каталог не говорит, как собрать `check[]` и что передавать |
| запросы с > 4 ключами | — | 3^n состояний; ограничение объёма, как у `shimTriConsistentFn` (не более 4 MAYBE) |
| эталон — `consistent`, а не SQL-оператор над записью | `extractValue` и записи | закону про triConsistent записи не нужны; закон «`check[]` из реальной записи → оператор» потребует роли value_extract — не делал |
| префиксные операнды (`a:*`) | comparePartial | закону не нужен; в выборку не включал |

## Consequence

Тот же K3, новая таблица ролей, новый протокол вызова — и закон GIN
`triConsistent` проверяется без отдельного «GIN-закона».  Конструкция
«закон + таблица ролей + протокол + источник значений» выдержала
четвёртый AM; потребовалось одно уточнение области значений эталона.
