# D1: закон + таблица ролей → проверки разных opclass

Вопрос: можно ли один и тот же закон плюс таблицу смысловых ролей
превратить в проверки разных opclass без AM-специфичного кода проверки.

Код: `d1laws/`.  Модель: ROLE-MODEL.md.

- движок законов `d1laws--0.1.sql`: K1–K6, разрешение ролей через каталог,
  без имён AM и без номеров support-функций/стратегий (grep по словам
  `btree|hash|gist|…` и по `amprocnum = N`/`*_PROC` пуст; `hash` в
  словаре — имя роли, не AM);
- таблицы ролей и экземпляры законов `role_tables.sql` — данные: btree и
  hash на уровне AM, GiST `poly_ops` на уровне семейства;
- вызов: любая роль вызывается по OID (`d1_invoke_*`), не по имени;
- адаптеры протоколов (`d1laws.c`) для support-функций с
  `internal`-сигнатурой: `sortsupport`, `abbrev`, `skipsupport`,
  `entry_consistent`.

## Result

Да, для трёх разных AM.  Один движок с тремя таблицами ролей проверил
законы btree (O1–O9), hash (H1–H6) и GiST `poly_ops` (G1).  Для btree
результат совпал с отдельным btree-проверяльщиком `opclass_laws` закон
за законом на пяти opclass/collation и на всех 11 контрольных отказах.

Один и тот же K3 выразил и abbreviated keys btree, и consistent GiST.

## Контрольные примеры

Каждый отказ меняет одно отношение; видно, какие законы падают.

| opclass | отказ | падают |
|---|---|---|
| btree ctl_int4_ops | 11 отказов из `opclass_laws` | ровно те же законы, что у `opclass_laws`, по всем 11 (в т. ч. skip_symmetric → O9) |
| hash ctl_hash_int4_ops (равенство mod 1000) | eq_nontransitive | H3, H4, H5 |
| | hash_congruence | H4, H6 |
| | hash_extended | H6 |
| GiST ctl_poly_ops | consistent_exact (recheck = false при потерях) | G1: `strategy 1: x=((0,0),(4,0),(0,4)) q=((4,4),(1,4),(4,1)) answer=1 flag=f reference=0` |
| btree ir_int4_ops (`in_range` с «дыркой») | inrange_val (false при val = 2) | O8 [val]: FAIL; O8 [base]: pass |
| | inrange_base (false при base = 3) | O8 [base]: FAIL; O8 [val]: pass |
| btree без support-функций 2–6 | — | O5, O6, O8, O9: n/a (роль отсутствует), не FAIL |

Падения нескольких законов от одного отказа ожидаемы: сломанное
отношение (равенство, хеш) входит в несколько законов.

Красные пробы движка (ломался движок, не opclass): отключение
транзитивности K1, правила доверия K3, следствия K4, low32 в K2, учёта
ролей семейства — каждое даёт красный стенд.

K5 считает и сообщает две половины отдельно (`checked_val`,
`checked_base`; строки `O8 [val]` и `O8 [base]`).  У каждой своя
контрольная «дырка» в одном аргументе, которая оставляет монотонным другой
аргумент; отключение любой половины в движке даёт красный стенд.

K6: отключение одной проверки «нет пропуска» (только вверх) остаётся
зелёным, обеих — красное.  Это следует из логики: обратимость шага вместе
с проверкой «нет пропуска вниз» покрывает пропуск вверх.

Отрицательный результат: сверка с `opclass_laws` нашла ошибку в самом
движке (K6: внутри `NOT EXISTS` неквалифицированное `v` разрешалось во
внутреннее `y.v`, проверка «нет пропуска» была пустой).  Исправлено.

## K3: одна конструкция для двух механизмов

    approx(x, q) → (answer, flag)        адаптер протокола
    trusted(answer, flag)                задаётся в экземпляре закона
    trusted ⇒ answer = reference(x, q)

| | abbreviated keys (O6) | GiST consistent (G1) |
|---|---|---|
| answer | знак сравнения сокращённых ключей | результат consistent (0/1) |
| flag | — | recheck |
| trusted | `answer ≠ 0` | `answer = 0 ∨ ¬flag` |
| reference | знак comparator | оператор стратегии |

Точное различие — не в законе, а в протоколе: abbreviated преобразует
**оба** значения и сравнивает преобразованные; consistent преобразует
только запись `x` (compress → leaf entry) и сравнивает с сырым запросом
`q`.  Это различие целиком живёт в адаптере.

## Границы

| граница | нужная информация | почему существующих метаданных недостаточно |
|---|---|---|
| O8 для date_ops | G: значения типа смещения (interval) | значения берутся из выборки типа date; каста date → interval нет (та же граница, что в D0) |
| роли с `internal`-сигнатурой: sortsupport, abbrev, skipsupport, consistent/compress | протокол вызова (какая структура передаётся, как читать ответ) | `pg_amproc` даёт OID и сигнатуру `internal`, но не соглашение о вызове.  Протокол назван в таблице ролей; адаптер знает соглашение (`SortSupport`, `SkipSupport`, `GISTENTRY` + leaf-страница), но не AM |
| GiST entry_consistent | полноценная запись индекса | адаптер строит leaf-страницу с флагом `F_LEAF` и `rel = NULL`; для `poly_ops` этого достаточно (gist_poly_consistent/compress не читают rel и содержимое страницы).  Функции, которые читают больше, потребуют более полного адаптера |
| guard с не-collatable аргументом (`equalimage(oid)`) | collation вызова | у функции нет collatable аргумента, каталог не говорит, что она зависит от collation; движок передаёт collation выборки через значение-носитель |
| проверки только на одном GiST opclass | — | не граница модели, а объём эксперимента |

Наблюдение про GiST: для K3 таблице ролей семейства хватило трёх строк
(consistent, compress, «все поисковые операторы»).  Смысл отдельных
стратегий не понадобился: эталон — сам оператор стратегии.

## Consequence

Конструкция «закон + таблица ролей» работает на трёх разных AM: код
проверки общий, AM-специфичны только данные (таблица ролей) и
соглашения о вызове `internal`-функций (адаптеры протоколов).  Итоговая
формула (ROLE-MODEL.md):

    semantic law + role binding + call protocol + value source = generated check
