# InterfaceSpec v1 architecture review

База: `main = d99fccd`.  Источники — только закрытые эксперименты D0–D3 и
их документы (README, BT-INV, INTERFACE-GENERALITY, DERIVATION-MAP,
INTERFACESPEC-EVIDENCE, ROLE-MODEL, PROTOCOL-MODEL, D0…D3-*-RESULT,
`interfacespec-v0.yaml`, `protocolspec-v0.yaml`, `concurrencyspec-v0.yaml`).
Новых экспериментов и кода нет.  Где вывод не подтверждён экспериментом,
он помечен «гипотеза».

Критерий для каждой сущности: где впервые понадобилась; какую историю или
закон без неё нельзя выразить; есть ли контроль или red probe, который без
неё не ловится; semantic это или harness.

## 2. Layers D0-D3

D0–D3 — история эксперимента, а не уровни языка.  Они смешивают три
независимые оси:

| ось | значения | D0 | D1 | D2 | S6 | S5 | V5 |
|---|---|---|---|---|---|---|---|
| состояние | stateless / stateful | stateless | stateless | stateful | stateful | stateful | stateful |
| участники | один / несколько | один | один | один (два скана одной сессии — S7) | несколько | несколько | несколько |
| граница наблюдения | компонент / взаимодействие / end-to-end | end-to-end (SQL) | компонент (support-функции) | компонент (callback'и) + взаимодействие (lifetime для исполнителя) | компонент | компонент | end-to-end |

Например, D0 и V5 оба end-to-end, а D1 и D2 оба компонентные.  Порядок D0 → D3 —
порядок, в котором вопросы задавались, а не иерархия включения: V5 не
надстройка над S5.

Рекомендация для v1 (без переименования в репозитории): говорить о
**модулях** по смыслу — metadata/capability, value laws, lifecycle
protocol, concurrency, end-to-end composition — и о трёх осях выше.
Названия D0–D3 оставить как имена экспериментов.

## 3. Minimal semantic entities

Только то, без чего хотя бы один закон не выражается.  Таблица с
источниками — INTERFACESPEC-V1-MATRIX.md.

**Interface, Capability.**  Объект контракта и то, что реализация заявляет
о себе (флаги и callback'и IndexAmRoutine).  D0 выводит из capability
импликации (A2, A4, A6, A7, A9, A10); D2/D3 отсекают операции по
`requires` (n/a для hash/GiST в S5).  Источник — runtime, не декларация:
v0 перечисляет, но не загружает capabilities.

**Role, Binding, Invocation.**  Остаются тремя сущностями.  Доказательство
раздельности: btree support 2 — одна процедура, две роли
(`alternate_comparator`, `approximate_comparator`), две invocation
(`sortsupport`, `abbrev`); GiST — та же роль `consistent`, binding на
уровне opfamily, другой invocation (`entry_consistent`); GIN —
`consistent` с invocation `key_vector_bool`.  Слить binding и invocation
нельзя: одно и то же «где» с двумя «как».  Слить role и binding нельзя:
одна роль — разные номера у разных AM и семейств.

**Law.**  Отношение над наблюдениями ролей или операций; вид (K1–K6),
отношение, доверенное направление (K3).  В D2 тот же закон записан как
`expect` (наблюдение = значение модели), в D3 — как allowed outcomes.

**Obligation и Domain** — центральный результат D2:

- obligation — документированное требование к вызывающему; нарушение —
  вина вызывающего (`refused`, на трафике executor'а — ERROR).  Пример:
  первый Backward только при `amcanorder`; `amrescan.nkeys <=
  ambeginscan.nkeys`;
- domain — область, где интерфейс определяет поведение, не требуя ничего
  от вызывающего; вне неё истории не генерируются и не проверяются, а
  вызывающий не обвиняется.  Пример: повтор направления после `false`;
  restore без mark.

Без разделения первая версия D2 сделала недокументированное поведение
nbtree/hash нормативным контрактом.  D2 `guard` — не отдельная сущность, а
obligation над аргументами с точкой принуждения «до передачи вызова».

**State, Operation, Effect.**  Состояние объекта (скана), операция =
callback с аргументами и `requires`, effect = новые значения полей.
Transition и sequence constraint не понадобились: выражаются через effect
и obligation/domain над полями state (PROTOCOL-MODEL).

**Observable (с lifetime и границей наблюдения).**  Что видно и где: TID и
bool на границе callback'а; `xs_itup`/`xs_hitup` с lifetime (S7, R8);
строки результата SQL (D0, V5).  V5 показал, что граница наблюдения —
атрибут observable/actor, а не константа языка: тот же индекс,
наблюдаемый на границе callback'а, не нарушает S6, а наблюдаемый на
границе исполнителя — нарушает закон видимости.

**Actor.**  Участник истории: A (скан), B (другая сессия, между
callback'ами A), A2 (скан исполнителя, курсор).  Без B не выражается S6;
без A2 — V5.

**Allowed outcomes.**  Множество допустимых наблюдений вместо одного
значения.  Встретилось дважды и независимо: K3 (доверенный ответ или «не
знаю»; эталон тоже может сказать «не знаю») и S6 (must / may / must_not,
gap).  Общая форма: отношение «наблюдение допустимо относительно эталона».
must/may/must_not — DSL-форма для множеств записей; trusted/unknown —
форма для приближённых ответов; точное равенство — вырожденный случай
(D0, V5).  Один ли это механизм в языке — гипотеза: общий вид есть, общей
схемы ещё никто не исполнял.

**Reference** (нормативная часть) — см. §4 про разделение с oracle.

## 4. Harness/evidence entities

| понятие | где | почему не семантика |
|---|---|---|
| Oracle (исполняемый эталон): seqscan, forward pass того же AM, свежий скан индекса из третьей сессии, seqscan под снимком A2 | D0, D2, S6, V5 | способ вычислить нормативный эталон; заменяем без изменения закона (D2: forward pass сверен с seqscan) |
| Value source: sample, cast, generated | D0, D1 | откуда взять значения; закон о них не говорит.  Исключение — completions (GIN): «для каждого доопределения» — квантор закона, его нельзя заменить выборкой (контроль `tri_first_completion`) |
| Generation profile: prologue, alphabet, limits, order, depth | D2, D3 | какие истории строить; контракт его не содержит |
| Coverage requirement | S5, S6, V5 | условие доказательности прогона, не закона (§10) |
| Состояние операции B: completed / blocked (`pg_stat_activity`) | S6 | планирование: когда смотреть.  Проба Q6 S6: если сделать «remove начался» семантикой, контрпример с заблокированным VACUUM исчезает — классификация обязана идти по наблюдению содержимого индекса |
| Identity строки/записи в стенде: heap TID (S6), логический `id` (V5) | S6, V5 | представление наблюдателя (§8 про identity) |
| Evidence: счётчики, контрпримеры, BOUNDARY-числа, pin/wait события | D3 | зависят от планирования и чужого xmin; не вердикт |
| Controls, red probes | все | метапроверка: стенд ловит то, что обещает ловить |

## 5. Boundaries between layers

- **Значения vs история.**  D1 (stateless) и D2 (stateful) не делят
  сущностей, кроме capability: role/law/value source в D2 не
  использовались (PROTOCOL-MODEL).  Закон D2 по форме тот же (наблюдение
  совпадает с эталоном), но эталон вычисляется моделью по истории.
- **Один участник vs несколько.**  D3 не изменил ни protocolspec, ни
  движок D2: concurrency — дельта над lifecycle (actor + allowed outcomes).
  S5 подтвердил: concurrency добавила к mark/restore только поле состояния
  (gap), а не новую сущность.  Итог: S5-concurrent expanded state, not the
  ontology.
- **Компонент vs end-to-end.**  V5: закон видимости не выражается на
  границе callback'а — выдача записи удалённой строки там допустима по S6.
  Нарушение появляется только у потребителя (исполнитель + VM).
- **Семантика vs механизм** — §6.

## 6. Law vs refinement

Кандидат в критерий: инвариант — law InterfaceSpec, если его нарушение
определяется через интерфейсно наблюдаемое поведение, без механизма
реализации.  Если формулировке нужны page, buffer, pin, LSN, private AM
state — вероятно, refinement.

Проверка по примерам:

| пример | наблюдаемое | вердикт |
|---|---|---|
| V5 «index-only scan не снимает pin» | pin | refinement закона «результат = строки, видимые снимку» (V5-RESULT) |
| V3 в sgml «скан держит pin на последней странице» | pin | документация записала механизм как контракт; btree законно его ослабляет для MVCC (R2), закон S6/видимости при этом выполнен.  Механизм в DOC — ещё не law |
| V4 LSN-гейт для LP_DEAD | LSN | refinement S10 (kill hint не скрывает видимую запись) |
| V6 safexid, S14 L&Y, T1–T13 структура | page, sibling links | refinement S1/S3/S4 |
| S7 lifetime `xs_itup` (R8) | байты возвращённых данных между callback'ами | law: наблюдаемо на границе, механизма не называет |
| S6 | записи, выданные callback'ом | law |
| O7 equalimage | `datum_image_eq` — свойство значения, не AM | law |
| **S11** «`amendscan` освобождает pin'ы и lock'и» | pin | **контрпример критерию**: pin здесь — ресурс, которым интерфейс владеет и который обязан вернуть, а не механизм другого свойства |
| A11 handler возвращает постоянную структуру | память | то же: ownership/lifetime объекта интерфейса |

Уточнённый критерий:

1. Нарушение формулируется через наблюдаемое на границе интерфейса или
   через результат потребителя (end-to-end).
2. Если в формулировке есть внутренний объект (pin, page, буфер), он
   допустим только как ресурс, которым интерфейс владеет и состояние
   которого видно на границе (S11, A11).  Если внутренний объект нужен как
   средство обеспечить другое наблюдаемое свойство, это refinement того
   свойства (V3, V4, V5).
3. Утверждение, записанное в документации как механизм (V3 в sgml), само
   по себе не law: R2 показывает, что реализация может законно его не
   выполнять, если наблюдаемый закон цел.

## 7. AM vs executor boundary

V5 впервые проверил контракт за пределами callback-границы AM.  Нужны три
уровня — их требуют разные строки результатов, а не схема:

| уровень | граница | примеры | кто отвечает |
|---|---|---|---|
| component contract | вызовы одного интерфейса | S4, S5, S6, S8, D1-законы | реализация интерфейса (AM, opclass) |
| interaction contract | передача результата между компонентами | S7 (lifetime данных для исполнителя, R8); interlock «TID, выданный index-only скану, не становится переиспользуемым до проверки VM» (R9) | обе стороны: AM и исполнитель/table AM |
| end-to-end contract | результат запроса | S1-ext, S9-ext, A6 (D0); видимость снимку (V5) | система целиком |

Ответ на вопрос «где заканчивается Index AM InterfaceSpec»: на interaction
contract.  Index AM InterfaceSpec описывает component contract плюс свою
сторону interaction contracts: что AM обязан обеспечить, чтобы потребитель
мог выполнить свой закон (lifetime `xs_itup`, interlock для index-only).
End-to-end закон (видимость снимку) принадлежит исполнителю/table AM; AM
к нему причастен только через interaction contract.

В PostgreSQL сторона AM этого interaction contract не записана (R9):
indexam.sgml разрешает асинхронный скан при MVCC (1157–1167) и называет
VM «no concern of the access method's» (1036–1043).  Проверить её только
на границе AM нельзя: нарушение видно, лишь когда исполнитель использует
VM.  Поэтому V5 проверяет end-to-end закон, а interaction contract виден
через control (`collect_all`) и реальный GiST.

Открытый вопрос: формулировать ли сторону AM как отдельный law
(«для `xs_want_itup` выданная запись не может быть удалена VACUUM'ом
раньше, чем потребитель проверит видимость») — тогда ему нужен наблюдатель
VM или heap, то есть уже не граница AM.

## 9. What v0 got right

- Capabilities берутся из runtime, а не объявляются: D0 работает на
  сторонних AM без декларации.
- Role / binding / invocation разведены; закон не знает номеров, binding
  не знает соглашения о вызове, invocation не знает смысла (D1 на четырёх
  AM).
- Виды законов K1–K6 с доверенным направлением: K3 выразил три механизма
  (abbrev, GiST consistent, GIN triConsistent).
- Value source вынесен из закона.
- Данные отдельно от движков; round trip YAML → таблицы → неизменённый
  тест (`interfacespec/check_v0.sh`).
- Каждая следующая spec — дельта над предыдущей без её изменения
  (protocolspec над v0, concurrencyspec над protocolspec): за D2–V5 ни
  один expected предыдущих уровней не поменялся по семантике.

## 10. What v0 is missing

Всё ниже уже существует в protocolspec/concurrencyspec, но не в v0:

| чего нет в v0 | кто потребовал |
|---|---|
| state, operation, effect | D2 (S4, S5, S8) |
| разделение obligation / domain | D2 (повтор после false, mark/restore) |
| observable с lifetime и границей наблюдения | S7 (R8), V5 |
| actor | S6, V5 |
| allowed outcomes | K3 (частично есть в v0 как `trusted`), S6 |
| нормативный reference отдельно от oracle | §4, V5 |
| coverage requirement | S6, S5, V5 |
| словарь вердиктов (ниже) | D0, D1, D2, D3 возникали независимо |
| единая терминология | слово `protocol` (D1/D2), слово `guard` (D1/D2) перегружены |

**Терминология.**

- D1 `protocol` → **invocation**: соглашение о вызове одной функции
  (`plain`, `sortsupport`, `abbrev`, `entry_consistent`, `key_vector`…).
  Не `call_shape`: `shape` уже атрибут роли (cmp, rel, approx…).  Не
  `call_adapter`: адаптер — реализация invocation в C, а не понятие spec.
- D2 `protocol` → **protocol** (lifecycle protocol): порядок операций над
  объектом с состоянием.  Слово остаётся за D2, потому что именно так его
  понимают в PostgreSQL («scan protocol»).
- D1 `guard` (`image_equivalence`) → **claim**: opclass заявляет, что закон
  к нему применим; ответ «нет» — `n/a`.  D2 `guard` → часть
  **obligation** (обязательство над аргументами, проверяемое до передачи
  вызова).  Сейчас одно слово обозначает и условие применимости закона, и
  точку принуждения обязательства.

**Словарь v1** (по одному примеру из экспериментов):

| термин | значение | пример |
|---|---|---|
| capability | что реализация заявляет о себе | `amcanorder` |
| claim | заявление реализации, включающее закон | equalimage → O7 |
| caller obligation | документированное требование к вызывающему | первый Backward только при `amcanorder` (S4) |
| domain restriction | где поведение определено; вне — не проверяется и не обвиняется | restore без mark; повтор направления после `false` |
| implementation guarantee | постусловие операции в домене | restore возвращает к метке (S5); данные живут до следующего вызова (S7) |
| semantic law | отношение над наблюдениями, не зависящее от истории вызовов | O1 рефлексивность cmp; K3 доверенный ответ |
| allowed outcomes | допустимое множество наблюдений | S6 must/may/must_not |
| refinement invariant | механизм, обеспечивающий закон в одной реализации | V5 pin |

`invariant` без уточнения и `contract` как отдельная сущность в v1 не
нужны: «контракт» — общее имя записи каталога (S6, V5…), реализуемой одним
или несколькими терминами из таблицы.

**Вердикты** — строгие определения и проверка на всех случаях:

| состояние | определение | случаи |
|---|---|---|
| pass / FAIL | закон проверен на истории; FAIL — у реализации | везде |
| caller FAIL (`refused`) | нарушено obligation; виноват вызывающий | D2 `caller_more_keys` |
| n/a | у субъекта нет capability, роли или claim, которые требует закон | S5 на hash/GiST (нет `ammarkpos`); O8/O9 у text_ops (роли нет); O7 у text ci (claim = false); O6 у int4 (opclass отказался от abbreviation) |
| DOMAIN | история или исход вне области, где интерфейс что-либо обещает | D2: повтор направления после `false` (не генерируется); S5: повторная выдача удалённой помеченной записи (исход есть, вердикта нет) |
| BOUNDARY | интерфейс обещает, но стенд не может решить: не хватает входа, наблюдения или гранулярности чередований | D0/D1: значения другого типа (G); S6: TID переиспользован, наблюдатель не различает записи; V5: окно внутри одного вызова исполнителя (handoff) |
| UNRESOLVED | сам контракт не решён: документация и код расходятся | A3/A5 (R1, R3) |
| finding (METADATA и др.) | два источника утверждения расходятся; закон при этом может выполняться | R6 (`returnable` против `amcanreturn`) |
| not covered (`empty`, «none», «NOT tested») | вердикт есть, но обязательная область не достигнута | D0 `empty`; S6 «3 of 4»; V5 «none» |

Проверка определений: D2 DOMAIN — до генерации, S5 DOMAIN — по
наблюдённому исходу; это одно понятие, разное время применения.
BOUNDARY D0 (значения) и S6 (идентичность) — одно понятие (стенду чего-то
не хватает), с указанием, чего: входа, наблюдения или чередования.
`n/a` из-за отсутствия capability (S5) и из-за `claim = false` (O7) —
одно и то же, если claim считать заявлением реализации о себе.  Отдельные
состояния UNRESOLVED и finding нужны: ни одно из определений выше их не
покрывает.

## 11. What should NOT go into v1

| понятие | причина |
|---|---|
| page, buffer, pin, LSN, sibling links, internal AM state | refinement only (§6); evidence допустимо |
| lock (как механизм скана) | refinement only; блокировка как семантика — deferred (U2) |
| resource (acquire/release) | deferred because no experiment (S11 не исполнен) |
| WAL, recovery | deferred because no experiment (T16, V8) |
| transaction object | not needed yet: в V5 снимок — параметр actor'а (`isolation`) и эталона («тот же снимок»), отдельная сущность не понадобилась |
| transition (from, op, to) | not needed: effect + obligation/domain (D2) |
| sequence constraint | not needed: domain над полями state (D2) |
| precondition как одно понятие | вредно: распалось на obligation и domain (D2) |
| identity как сущность | not needed yet (§12): атрибут observable, а не сущность |
| operation state (completed/blocked) | harness (S6 Q6); семантика — deferred до U2 |
| D1 guard как отдельная сущность | сливается с claim (n/a) |
| D2 guard как отдельная сущность | сливается с obligation |
| refinement-связь «закон ← механизм» | не нужна для проверки; документируется в результатах |

## 12. Candidate v1 model

Минимальный набор; объединено то, что оказалось одним понятием.

**Semantic:**

| entity | первым потребовал | зачем | доказательство (control/probe) |
|---|---|---|---|
| Interface | D0 | объект контракта | — |
| Capability (+ claim) | D0, D1 (O7) | что реализация заявляет; n/a | n/a на hash/GiST в S5; O7 text ci |
| Role | D1 | смысл функции | красные пробы движка D1 (учёт ролей семейства) |
| Binding | D1 (GiST opfamily) | где реализована роль | GiST на уровне opfamily; probe «удалён G1» |
| Invocation | D1 | как вызвать | support 2: две invocation; GIN `key_vector` |
| Law (с allowed outcomes) | D1, S6 | что должно выполняться | все контроли D1; Q1–Q5 S6 |
| Obligation | D2 | вина вызывающего | `caller_more_keys`; P4 |
| Domain | D2 | где поведение определено | P3 (генерация вне domain даёт красный стенд) |
| State, Operation, Effect | D2 | lifecycle | P2 (модель без позиции) |
| Observable (lifetime, boundary, identity как атрибут) | D2 (S7), V5 | что и где видно | P1, P6 (lifetime); `collect_all` index-only против plain (boundary) |
| Actor | S6, V5 | несколько участников | все S6/S5/V5 контроли |
| Reference (нормативный) | D0, D1 | с чем сравнивать по смыслу | M6 (охрана эталона D0); GIN «не знаю» |

**Harness (часть исполняемой spec, но не контракта):** Oracle,
ValueSource (кроме кванторов закона), GenerationProfile,
CoverageRequirement, Evidence, Controls.

Связи:

    Interface ── Capability/claim ─────────────── n/a
        │
        ├── Role ── Binding ── Invocation           (value laws)
        │      \
        │       Law ──── Reference (normative) ───── Oracle (harness)
        │        │  allowed outcomes                 ValueSource (harness)
        │        │
        ├── Operation ── State ── Effect             (lifecycle)
        │      │  Obligation (caller)   Domain (DOMAIN)
        │      │
        │   Observable (boundary, lifetime, identity)
        │      │
        └── Actor ── histories ── GenerationProfile (harness)
                                     │
                               CoverageRequirement (harness)
                               Evidence (harness)

Law связывает либо роли (value laws), либо наблюдения операций в
истории (lifecycle/concurrency); allowed outcomes — форма отношения в
обоих случаях.  Actor исполняет операции; observable задаёт, на какой
границе исход наблюдается.

Coverage — не сущность контракта.  Это условие доказательности прогона:
закон говорит, что должно выполняться; GenerationProfile — какие истории
строить; CoverageRequirement — какие семантические области должны быть
реально достигнуты, иначе зелёный вердикт ничего не значит.  В отличие от
обычного regression expected, это проверка самого стенда.  Место в v1 —
рядом с GenerationProfile, в harness-части.

Reference: в D1 эталон — другая роль того же интерфейса (оператор
стратегии, comparator, consistent), то есть часть закона.  В D0, D2, S6,
V5 эталон — независимый путь вычисления того же нормативного множества
(seqscan, forward pass, скан индекса из третьей сессии, seqscan под
снимком).  Поэтому разделение: Reference — нормативное «с чем сравнивать
по смыслу» (множество подходящих записей; множество строк, видимых
снимку; ответ роли-эталона), Oracle — способ его вычислить.  P1 V5
показывает, что oracle несёт семантические параметры (тот же снимок):
неверный oracle даёт ложный FAIL.

Identity: S6 отождествлял записи по heap TID, и при переиспользовании TID
наблюдатель не различал записи — BOUNDARY.  В V5 закон сформулирован над
строками результата, и логический `id` — свойство данных стенда, а не
закона; путаница по TID при MVCC-снимке оказалась ненаблюдаемой.  Но S6
сам говорит о «тех же записях» (не пропустить, не выдать дважды), значит
закону нужна идентичность записи — та, которую даёт интерфейс (TID +
данные).  Вывод: identity — атрибут observable («по чему различаются
исходы»), BOUNDARY возникает, когда identity наблюдателя грубее, чем
нужна закону.  Отдельная сущность не нужна, пока ни один закон не
потребовал идентичности, которой нет в интерфейсе.

## 13. Open questions

1. Единая v1 schema или несколько composable specs.  Свидетельство за
   composable: три дельты без изменения предыдущих, ни один старый
   expected не поменялся по семантике.  Против: конфликт терминов
   (`protocol`, `guard`) и повтор понятий (reference, n/a) в трёх файлах.
   Предложение: один словарь (этот документ + MATRIX) и несколько модулей
   spec, которые ссылаются на общие понятия; одну схему не делать, пока
   не появится второй интерфейс (не Index AM).
2. Allowed outcomes как одна сущность: K3 (trusted/unknown) и S6
   (must/may/must_not) — один вид или два.  Нужен закон, где они
   встречаются вместе (приближённый ответ при конкуренции — например,
   recheck GiST под S6).
3. Interaction contract AM → executor для index-only scan (§7): отдельный
   law со стороны AM или только end-to-end закон + control.
4. U2: блокировка как семантика.  Если да, completed/blocked переходит из
   harness в observable.
5. Resource (S11) и lifetime handler'а (A11): одна сущность ownership или
   две.
6. Снимок: параметр actor и reference (как сейчас) или сущность, когда
   появятся non-MVCC снимки (DOC п. 4 V5-RESULT: для них plain scan тоже
   требует interlock).
7. UNRESOLVED A3/A5: кто решает — документация или код (R1, R3).
   InterfaceSpec здесь заставляет принять решение, но сам его не
   принимает.
8. R1–R9 по типам (ниже): поможет ли эта таксономия выбирать уровень
   проверки для нового интерфейса.

**R1–R9 как архитектурные данные.**

| тип расхождения | R | где InterfaceSpec его видит |
|---|---|---|
| документация строже кода | R1 (A3: mark/restore обязательны) | capability-импликация, UNRESOLVED |
| документация записала механизм; реализация законно слабее | R2 (V3 pin vs MVCC) | закон цел (S6, V5); механизм — refinement |
| документация и код расходятся, решения нет | R3 (A5 backward ⇔ amcanorder) | UNRESOLVED |
| проверка формы слабее закона | R4 (`amvalidate` пропускает opclass без законов) | D1 законы против каталога |
| документация неполна (перечень) | R5 (interval и equalimage) | D1 K4 + claim |
| metadata mismatch | R6 (`returnable` против `amcanreturn`) | D0, два пути метаданных |
| интерфейс против ABI ядра | R7 (nkeys ≤ против ==) | D2 obligation/guard |
| lifetime mismatch | R8 (restore меняет `xs_itup`) | D2 observable.lifetime |
| end-to-end correctness bug, документация неполна | R9 (GiST index-only) | end-to-end закон + interaction contract |

R1–R8 — расхождения между описаниями (документация, каталог, код) при
правильном результате запроса.  Их видно на уровне component contract или
метаданных.  R9 — первое расхождение, меняющее результат, и оно видно
только end-to-end.  Таксономия говорит, где проверять: несогласованность
описаний — в компонентном слое и метаданных; неверный результат — там,
где результат потребляется.

## 14. Consequence

InterfaceSpec — исполняемое описание наблюдаемого контракта интерфейса
расширяемости.  В него входят:
- что реализация заявляет о себе (capability, claim);
- какие законы связывают её функции и чем они реализованы (role, binding,
  invocation);
- как она ведёт себя на протяжении жизни объекта: требования к
  вызывающему, область определённого поведения, постусловия, время жизни
  данных;
- какие исходы допустимы, когда действуют другие участники;
- на какой границе (компонент, взаимодействие компонентов, результат
  запроса) и против какого нормативного эталона это решается.

Механизмы, которыми конкретная реализация выполняет закон (pin, LSN,
структура страниц), в контракт не входят, даже если записаны в
документации или проверяются amcheck.  Исполняемость добавляет
harness-часть, которая не является контрактом, но без которой
соответствие не доказано: oracle, источники значений, профили генерации,
обязательное покрытие и evidence.
