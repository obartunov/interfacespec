# Карта выводимости: 29 «нет» + 16 «косвенно»

Для каждого контракта из BT-INV.md без прямой проверки в ванили: какого
входа достаточно, чтобы проверку можно было **вывести**, а не написать руками.
Классификация — суждение по тексту контрактов, не измерение.

## Входы

| Вход | Что это | Есть сегодня? |
|---|---|---|
| R | метаданные, которые PostgreSQL уже имеет в runtime и каталоге, без новой декларативной информации: `IndexAmRoutine` (флаги, наличие callback'ов, `amtranslatestrategy`), `pg_am`/`pg_opclass`/`pg_amop`/`pg_amproc`, свойства индекса и колонок | да; часть видна из SQL (`pg_indexam_has_property`, `pg_index_has_property`, `pg_index_column_has_property`), остальное (`amoptionalkey`, `amcanparallel`, `ammarkpos`) — только из C, без изменений ядра |
| G | источник значений для типов операндов | для операнда того же типа, что колонка, — бесплатно из самой колонки (плюс касты из `pg_cast`); для других типов — нет.  Не свойство AM и не API PostgreSQL: часть инфраструктуры генерации тестов |
| E | эталон результата: seqscan с тем же квалификатором | да, в самом движке |
| B | таблица ролей на уровне opfamily: какая support-функция/стратегия играет какую роль | нет; для btree/hash неявно задана фиксированными номерами |
| C | наблюдение на границе callback'ов (proxy над `IndexAmRoutine`) | нет; отложено решением «пока не трогать proxy» |
| K | модель конкуренции: интервал допустимой неопределённости (S6) + управление чередованием | нет; S6 существует только прозой |
| X | внутреннее устройство AM | не вход интерфейса |

## Карта

| Уровень | Нужно | Контракты | Кол-во |
|---|---|---|---|
| **D0** | R + G(колонка) + E | A1, A2, A3†, A4, A5†, A6, A7, A9, A10, S1-ext‡, S2, S3, S9-ext‡, S13 | **14** |
| **D1** | + B | O1–O11 (с O8b), кроме O12 | **12** |
| **D2** | + C | S4, S5 (одна сессия), S7, S8, S11, V1, V7, U4, O13; плюс callback-части S1 и S9‡ | **9** (+2 части) |
| **D3** | + K | S6, V3 (обязательство), V5 (наблюдаемое следствие: IOS против E при конкурентном VACUUM) | **3** |
| **?** | неясно | A11 — контракт handler/lifetime (постоянная структура, const); эталон seqscan тут ничего не даёт, механизм проверки не определён | **1** |
| **—** | не выводится из интерфейса | V4, V6 (механизм nbtree: LSN-гейт, safexid), V8 (нужен стенд standby), V2 (обязательство ядра, не AM), S12 (не наблюдаемо), O12 (нужна вторая среда) | **6** |

† **UNRESOLVED.** A3 и A5 выводятся механически и входят в D0, но
генератор их пропускает: сначала надо решить R1 и R3 — документация или
код задаёт контракт.  Иначе генератор закрепит в тестах нерешённый вопрос.
Генерируемая часть D0 — 12 контрактов.

S7 — в D2: время жизни `xs_itup`/`xs_hitup` («валидны до следующего
вызова») видно только между callback-вызовами.  E проверяет значения
index-only скана, но не их время жизни.

‡ В D0 входят только внешние проекции S1 и S9 (результат исполнения =
эталон).  Их callback-части — точность при `xs_recheck = false`,
`amgetbitmap` ≡ объединение `amgettuple` — требуют C и относятся к D2.
Для AM с recheck проекция слабее контракта (BT-INV, после таблицы S).

Итого 14 + 12 + 9 + 3 + 1 + 6 = 45 контрактов; S1 и S9 разделены между
D0 и D2.

## Что из этого следует

- **14 из 45 выводятся из того, что PostgreSQL уже знает** — существующих
  метаданных и эталона seqscan (12 из них генерируются сейчас, A3/A5 ждут
  решения R1/R3).  Для них расширять интерфейс не нужно.
  Эти проверки просто никто не генерирует.  Большая часть флагов видна
  из SQL, так что генератор D0 применим и к сторонним AM.
- Для **S1 декларация профиля не нужна**: `xs_recheck` возвращается на
  каждой записи, поэтому точность проверяется по факту — при
  `xs_recheck = false` результат обязан совпасть с E.  Объявлять заранее
  нужно меньше, чем я предполагал в INTERFACE-GENERALITY.
- **Одно расширение даёт 12 контрактов**: таблица ролей opfamily (B).  Для
  btree и hash её можно задать константой, поэтому O1–O9 и исполняются уже
  сейчас.  Для GiST/GIN нужна таблица на уровне семейства.
- **Самое ценное — меньше всего по числу: D3** (S6, V3, V5).  Именно там
  interlock скана и VACUUM, включая ослабленное правило nbtree из R2.
  Без явной модели S6 эталон при конкуренции даёт ложные расхождения, так
  что этот уровень нельзя вывести, пока S6 не записан как данные.
- 6 контрактов в интерфейсный стандарт не входят: это механизм AM или
  свойство среды.

## Проверка, которую можно сделать кодом

Гипотеза «D0 выводится без знания AM» проверяется одним генератором на
btree, hash и GiST: только существующие метаданные и эталон, без имени AM,
без `if (btree/hash/gist)`, без таблицы специальных правил.  Если
потребуется AM-специфичное знание, оно не добавляется, а записывается:
контракт, ожидаемый вход, недостающая информация, почему существующих
метаданных недостаточно.  Это и есть граница D0.
