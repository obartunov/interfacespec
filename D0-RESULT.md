# D0: один генератор, три AM

Вопрос: выводятся ли D0-проверки (DERIVATION-MAP.md) из метаданных,
которые PostgreSQL уже имеет, значений из самой колонки и эталона
seqscan — без знания AM.

Генератор: `d0gen/` (plpgsql + C-чтение `IndexAmRoutine`, без изменений
ядра).  В исходнике генератора нет ни одного имени AM (`grep -wiE
'btree|hash|gist|gin|brin|spgist'` пуст); имя AM — только данные теста.
Прогон: `t_int(int4)` — btree и hash, `t_rng(int4range)` — GiST.

## Result

Один и тот же генератор, не знающий названий AM, получил проверки из
существующих метаданных PostgreSQL и выполнил их на btree, hash и GiST.
Все 12 генерируемых D0-контрактов (A1, A2, A4, A6, A7, A9, A10, S1-ext,
S2, S3, S9-ext, S13; A3/A5 — UNRESOLVED) порождены одним кодом без
AM-специфичных веток.  Нарушений контрактов не найдено.  Там, где входов
не хватило, недостающая информация относится не к устройству AM, а к
генерации значений другого типа.

| AM | pass | empty | n/a | FAIL | BOUNDARY | METADATA | UNRESOLVED |
|---|---|---|---|---|---|---|---|
| btree | 92 | 18 | 0 | 0 | 0 | 0 | 2 |
| hash | 15 | 0 | 8 | 0 | 0 | 0 | 2 |
| GiST | 111 | 0 | 4 | 0 | 1 | 1 | 2 |

`FAIL` — нарушение контракта; `METADATA` — два пути получения метаданных
расходятся, контракт при этом выполнен.

S1-ext и S9-ext — внешние проекции: результат исполнения через индекс
равен эталону.  Callback-части S1 (точность при `xs_recheck = false`) и
S9 (`amgetbitmap` ≡ объединение `amgettuple`) не проверены: им нужен
уровень C (D2).  Для AM с recheck проекция слабее контракта.

Числа — из `expected/d0_three_ams.out`.

`empty` — эталон пуст или планировщик не выбрал проверяемый путь (для
btree в основном параллельный скан на селективных условиях); такие строки
не засчитаны как pass.

## Evidence

Отрицательные примеры (в том же тесте, те же функции, что вызывает
`d0_check`, на заведомо неверном входе) — все дают `FAIL`:

| проверка | неверный вход | результат |
|---|---|---|
| S1-ext/S9-ext (сравнение с эталоном) | индекс без строки, вставленной при `indisready = false`; btree, hash, GiST | FAIL, названа пропавшая строка |
| A6 | индекс без 5 NULL-строк | FAIL: эталон 1005 (105 NULL), index-only 1000 |
| A9, дубликат | unique-индекс без ключа 500, дубликат 500 вставлен | FAIL |
| A9, повторная вставка | удаление, которое ничего не удаляет (триггер) | FAIL |
| S3 | порядок, обратный эталонному (ASC и DESC) | FAIL |
| охрана эталона | путь seq не читает индекс, путь index читает | f / t |

Красные пробы генератора (одноразовый worktree, ломается генератор, не
AM): все семь мутаций дают красный стенд — M1 все запросы с первым
оператором, M2 сравнение всегда «равно», M3 A9 без вставки дубликата,
M4 S3 без проверки порядка, M5 A6 сравнивает index-only сам с собой,
M6 охрана эталона выключена, M7 повторная вставка A9 объявлена pass.
До отрицательных примеров M3–M5 и M7 оставались зелёными.

- Проверка плана: результат засчитывается, только если план читает этот
  индекс нужным узлом, не `Disabled`, для S13 — `Parallel Aware`; план
  эталона не должен читать этот индекс вовсе.
- Стенд `make installcheck` стабилен на повторных прогонах.

## Граница D0

| contract | expected input | missing information | why existing metadata are insufficient |
|---|---|---|---|
| S1-ext/S9-ext для `@>(anyrange, anyelement)` | константа типа элемента range для колонки `int4range` | G — источник значений этого типа | метаданные дают тип нужного аргумента (`pg_range.rngsubtype`), но не значение; значения берутся из колонки, а из `int4range` нет каста ни в каком контексте, который привёл бы парсер к этому оператору; `lower()` — знание о типе, а не метаданные интерфейса |

Граница — про типы, не про AM.  Из неё следует ещё один общий вход
генерации, G: источник значений для типов операндов.  Это не свойство AM
и не новый API PostgreSQL, а слой инфраструктуры генерации тестов.  Для
операнда того же типа, что колонка, G бесплатно даёт сама колонка; этот
эксперимент нашёл место, где этого недостаточно.

    метаданные PostgreSQL (R)
          |
          +-- G  генераторы значений
          +-- E  эталонная семантика
          v
    сгенерированные проверки

Закрылось существующими метаданными: 8 операторов с правым операндом
`anymultirange` — константа получается explicit-кастом из `pg_cast`, а
оператор, который выберет парсер, проверяется точно (`:opno` в
сохранённом представлении).

## Расхождение метаданных (R6) — отдельная поправка, не InterfaceSpec

GiST, INCLUDE-колонка: `pg_index_column_has_property(idx, 2, 'returnable')`
возвращает NULL, а `amcanreturn` — true, и index-only scan по этой колонке
реально строится.  Причина в коде: `gistproperty` (gistutil.c:933)
отвечает на `AMPROP_RETURNABLE` через opclass колонки, у INCLUDE-колонки
opclass нет → `*isnull = true`; `gistcanreturn` (gistget.c:807) для
включённых атрибутов возвращает true.  Контракт A7 выполнен; неверен
SQL-видимый ответ.  Документация определяет `returnable` как «может ли
index-only scan вернуть значение колонки» (func-info.sgml:2234), а
`AMPROP_RETURNABLE` в `amproperty` — как более дешёвую замену вызова
`amcanreturn` (indexam.sgml:580), так что ответы обязаны совпадать.
Обсуждения в pgsql-hackers не нашёл.  SP-GiST `AMPROP_RETURNABLE` сам не
обрабатывает (идёт общий путь через `amcanreturn`), так что по коду это
только GiST.  Оформлять отдельным маленьким патчем с регрессионным
тестом на GiST INCLUDE, не в составе InterfaceSpec.

Сверка `returnable` с `amcanreturn` для ключевой колонки: совпадает на
btree, hash и GiST; расхождение R6 — только у INCLUDE-колонки GiST.

## Что пришлось взять из C, а не из SQL

`amoptionalkey`, `amcanparallel`, наличие callback'ов, `amcanreturn`
(прямой ответ AM), `amtranslatestrategy`, `GetDefaultOpClass`.  Всё это
существующий runtime, новой декларации не потребовалось.

## Отрицательные результаты (ошибки генератора, найдены его же тестом)

- Режим index-only сначала выключал сам себя: `enable_indexscan = off`
  запрещает и index-only пути (planner.c:496–511).  A6 давал `empty` не
  из-за AM.
- Константы «первые по ctid» давали проверки на 0 строк, которые
  засчитывались как pass.  Теперь константы разнесены по колонке, пустой
  эталон — `empty`.

## Consequence

Независимость D0 от AM подтверждена на трёх AM.  Утверждение, что для
всех D0-проверок достаточно R + E, оказалось слишком сильным: нужен ещё
G, и граница D0 впервые найдена работающим общим кодом, а не
предположена.  Ограничение: A4, A9, S3, S13
реально исполнены только на btree — среди встроенных AM только у него
соответствующие флаги (`amcanorder`, `amcanunique`, `amcanparallel`);
на hash и GiST генератор честно дал `n/a`.  Общность этих четырёх
подтверждена отсутствием ветвления, но не вторым исполнением.
